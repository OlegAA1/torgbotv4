# Серверный paper-терминал

## Границы готовности

Linux + Docker Engine + Compose v2. Node 24, pnpm 10.11.0, lockfile зависимостей.
Работает production-сборка vinext, а не dev-сервер/Miniflare. SQLite располагается
в постоянном Docker volume. Одновременно разрешён ОДИН экземпляр приложения:
масштабирование и несколько процессов, меняющих один торговый журнал, не поддержаны.

Эта инструкция не означает, что сервер уже развёрнут. Реальные биржевые ордера
не отправляются. Точность стратегии, старые проблемы учёта и восполнение всех
минутных свечей после простоя не исправлены инфраструктурным обновлением.
Аптайм сервера сам по себе не гарантирует котировки или исполнение TP/SL.

## Первая установка

Из папки `versions/2026-10-03-server-ready/Trading_Terminal`:

```sh
# Node на хосте не обязателен: генерируем секреты одноразовым контейнером.
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/app" -w /app node:24-bookworm-slim node scripts/init_server_env.mjs
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:3000/healthz
```

Секреты создаются в `.env.server` (права 0600), не печатаются и не коммитятся.
Храните этот файл отдельно от GitHub. Пользователь `admin`; пароль берётся из
`NORTHSTAR_ADMIN_PASSWORD`. Автоматизация изначально выключена.

По умолчанию порт опубликован ТОЛЬКО на loopback сервера. С компьютера:

```sh
ssh -L 3000:127.0.0.1:3000 user@SERVER
```

Откройте `http://localhost:3000`. Для другого локального порта измените также
`NORTHSTAR_PUBLIC_ORIGIN`. Для публичного домена нужен отдельный HTTPS reverse
proxy, точный `https://...` в этой переменной и закрытый прямой порт 3000.
Не публикуйте Basic Auth по незашифрованному HTTP. Все страницы, API и статика
требуют входа; только `/healthz` публичен и не выдаёт торговые данные.

Проверьте графики, пустой/перенесённый журнал, время котировок и доступность
источников. Затем установите `NORTHSTAR_AUTOMATION_ENABLED=1` в `.env.server`
и выполните `docker compose up -d --force-recreate`.
Paper-режим AUTO включается отдельно в интерфейсе после проверки данных.

## Наблюдение и ограничения

```sh
docker compose logs --tail=100 -f terminal
docker compose exec terminal node -e "fetch('http://127.0.0.1:3000/api/automation/status',{headers:{Authorization:'Bearer '+process.env.NORTHSTAR_AUTOMATION_TOKEN}}).then(r=>r.json()).then(console.log)"
```

Сканирование (обычно каждые 15 минут), сопровождение paper (обычно раз в минуту)
и heartbeat выполняются независимыми циклами; один и тот же цикл не перекрывается.
Интервал отсчитывается после завершения запроса, поэтому сетевые таймауты добавляют
задержку. Перезапуск при выходе процесса включён. Docker healthcheck сам НЕ
перезапускает зависший контейнер; для оповещения о stale heartbeat и недоступном
источнике нужен внешний мониторинг. Watchlist хранится в `/data/runtime/watchlist.json`,
журнал сканов — `/data/runtime/automation_runs.jsonl` (контролируйте размер).
Скальпинг остаётся браузерным; запуск веб-сервера не заменяет открытый скальп-раздел.

MOEX использует прямой ISS. Windows-мост `127.0.0.1:3021` на Linux отсутствует;
его необязательный fallback не является серверным источником. Проверьте доступ
к Bybit/OKX/Yahoo/MOEX с конкретного сервера до включения автоторговли.

## Telegram-уведомления

Необязательно. Сигналы «ГОТОВ», открытие и закрытие виртуальных сделок, запуск и остановка сервера
и проблемы сканера приходят в Telegram. Добавьте в `.env.server` `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID`, затем `docker compose up -d --force-recreate` и проверьте
`docker compose exec terminal node scripts/telegram_test.mjs`. Подробности, типы сообщений и
ограничения — в `docs/telegram-notifications-v1.md`. Это не замена внешнему мониторингу доступности.

## Резервирование и перенос

```sh
docker compose exec terminal node scripts/backup_server.mjs /backups/before-update.sqlite
docker compose cp terminal:/backups/before-update.sqlite ./before-update.sqlite
```

Используется SQLite backup API (включая WAL), результат проверяется `quick_check`.
Имя должно быть новым; существующий файл не перезаписывается. Копию обязательно
выносите с сервера. Не копируйте один основной sqlite-файл работающей базы без WAL.
Секреты резервируйте отдельно. Нельзя использовать `docker compose down -v`:
это удалит постоянные данные.

Для переноса локальной истории подготовьте согласованную SQLite-копию отдельно.
Остановите сервер `docker compose stop`, затем восстановите в `/data/terminal.sqlite`
из одноразового контейнера с тем же volume; WAL/SHM должны относиться к той же
копии, а не к предыдущей базе. Не переносите старые открытые позиции автоматически.
Перед импортом и восстановлением проверьте `quick_check`, число сделок, баланс,
права пользователя node (UID 1000) и сохраните старый volume/снимок. Импорт не
запускается автоматически, чтобы не смешивать локальные тесты с серверной историей.

## Обновление и откат

1. Разработка и тесты только локально/на отдельной тестовой базе.
2. Заморозить релиз и сохранить предыдущий image tag, `.env.server` и SQLite backup.
3. Проверить новую сборку на КОПИИ базы, без включённой автоматизации.
4. Только после приёмки остановить сервер, установить новый image и проверить
   `/healthz`, журнал, баланс, свежесть котировок и heartbeat.
5. При ошибке остановить новый образ и вернуть предыдущий. Если менялась схема,
   нужен согласованный снимок базы предыдущей версии; новые события при откате
   нельзя молча потерять. Сначала сохраните также повреждённую/новую базу.

Никаких автоматических `git pull`, смены правил и обновлений по расписанию.
Чистая установка и восстановление после перезагрузки должны пройти на целевом
Linux-хосте: локальные Node-тесты не заменяют проверку Docker Engine и провайдеров.
